## Purpose

Every other document in `/docs` answers "what is this system and why." This document answers a different question: **what is the current build status of everything that's been designed, and what order should remaining work happen in.** Design docs are largely static once locked. This document is meant to change constantly — treat it as the single place that reflects the actual current state of the project, not the intended-eventually state.

**Status legend:**
- 🟢 **Built & Functional** — exists in engine, works, playtested at least informally
- 🟡 **Partially Built** — some engine work exists but incomplete
- 🔴 **Designed Only** — fully specified in a doc, zero engine implementation
- ⚪ **Not Yet Designed** — acknowledged gap, no doc exists yet
- ⚫ **Explicitly Out of Scope** — deliberately not being pursued right now

## Known Defects — Found in Engine

New section as of July 15. These are distinct from the 🔴/🟡 rows above: those are *things not built yet*, these are *things built that don't work*. The distinction matters because implementation debt is predictable and defects are not — everything below was found by actually running the game, and none of it was visible from the code alone.

Six were filed the morning of July 15 from the first PIE pass that reached the Bestial Lucid. By that evening four were closed, one was made moot by a design change, and one remains. One new defect was found in the process. Resolutions are kept rather than deleted — the causes were non-obvious enough to be worth not rediscovering.

The night of July 15 added six more closures and three new open items. **Every single one was a silent failure** — no compile error, no warning, and in four cases a function that looked implemented and had zero callers or an empty Blueprint body. None were the hard systems. That is now the third session in a row where the difficult architecture was correct and the bugs were a capsule, an array, an unassigned field, and a notification nobody was listening to.

## Design Change — Phase 2 Trigger: Vital Index → Health Threshold

Decided and implemented July 15. Recorded because the reasoning matters more than the change.

**Was:** `Phase2TriggerVitalIndex = 2` — Phase 2 fired when the vital point shifted to a designated index.

**The problem:** vital shifts are driven by *two* things — an accumulated-damage threshold (`ShiftThreshold = 100.f`) and an independent looping timer (`bShiftOnTimer`, `ShiftTimerInterval = 5.f`) — and the index wraps modulo the array length. With the timer on and three vitals, index 2 was reached roughly 10 seconds after possess **whether or not the player had touched her.** It was a stopwatch. With the timer off it degraded to a flat 200 cumulative damage: better, but absolute, so it silently drifted every time her health was retuned, and it required the array to have at least three entries or Phase 2 could never fire at all.

**Now:** `Phase2HealthThreshold = 0.5f`, bound to the ASC's Health attribute change delegate. A *fraction* rather than a flat value, so it survives health retuning and scales when she's balanced for a full Kindle.

**What was lost:** nothing. The old trigger appeared to couple the phase to the vital point mechanic, but the coupling was invisible — no player counts vital shifts. The mechanic and the phase were never actually connected in a way anyone could perceive.

**What Phase 2 keeps:** the vital *freeze*, which is the real inversion. Phase 1 asks the player to track a moving target. Phase 2 stops hiding, resolves the vital to the heart, and makes the room the problem instead — the mechanic gets *easier* exactly when the fight gets harder. `HandleVitalPointShifted` remains bound but no longer owns the phase; a Phase 1 reaction to her own vital shifting is a plausible beat to want later.

## Vertical Slice Gate Checklist — What Actually Must Be True to Call This Done

Re-scoped after a full-project inventory surfaced significant confusion between "gating requirement" and "valuable future work." This section is the single, unambiguous answer to "what's left." Everything else in this document is real and correctly documented, but does **not** block the slice.

**Standing gotcha #2 — FName lookups fail silently, everywhere.** Added July 15 after it cost most of a session. `Blackboard->SetValueAsInt(FName, ...)` and its siblings return void and no-op silently when the key doesn't exist on the asset, or exists under a different type. No compile error, no log warning, and the symptom is indistinguishable from a logic bug — a boss stuck in Phase 0 forever. This bit `CurrentPhase` on BB_BestialLucid and cost a full debugging pass. The same exposure exists for every name in the `GothicBBKeys` namespace (`TargetActor`, `TargetLocation`, `bCanSeeTarget`, `bIsInCombat`, `PatrolOrigin`, `AttackRange`), which are C++-side promises that no blackboard asset is obligated to keep — currently honoured by BB_Enemy and BB_BestialLucid, but nothing enforces it for the next blackboard. ~~**The real fix, not yet built:**~~ **BUILT July 17.** `AGothicEnemyAIController::ValidateBlackboardKeys()` runs in `OnPossess` before any write, checking every `GothicBBKeys` name for existence *and type* (a `bIsInCombat` authored as a Float discards `SetValueAsBool` exactly as silently as a missing key) and logging `LogTemp Error` per problem. `BB_BestialLucid` failed it on first run and named its own missing keys. Also errors on an unassigned `BehaviorTreeAsset` and on `RunBehaviorTree` succeeding with a null Blackboard — both previously silent, both producing a motionless enemy. **Known gap:** it validates `GothicBBKeys` only, so subclass keys are uncovered — `AGothicBossAIController::PhaseBlackboardKey` ("CurrentPhase") is a `UPROPERTY` the validator never sees. Make `ValidateBlackboardKeys` virtual and override it on the boss controller.

**Standing gotcha #3 — OnRep never fires on the authority.** Added July 15 night after it silently disabled the Selah prompt for the only player who exists. `ReplicatedUsing = OnRep_X` fires **only on clients receiving replicated data** — never on the machine that authored the change, and never at all in standalone PIE, where no replication occurs. So a server-side `GS->ActivePromptCorpse = X; GS->ForceNetUpdate();` fired `OnEncounterPromptActivated` on remote clients only, and on nobody in the NetMode this project is actually tested in. **The fix pattern, now used by `SetActivePromptCorpse`:** a server-side setter that assigns, `ForceNetUpdate()`s, and then calls `OnRep_X()` by hand. The property was moved to `protected` with a `BlueprintPure` getter so direct assignment no longer compiles — the difference between fixing it and preventing it. **The same exposure exists on `UGothicVitalPointComponent::ActiveVitalIndex`**, which is why `ShiftVitalPoint` and `FreezeVitalPoint` both broadcast manually after assigning; any future replicated property with an OnRep needs the same treatment.

**Standing gotcha #4 — state that outlives the pawn cannot hold pawn pointers.** Added July 15 night, having now bitten twice. The player's ASC and AttributeSet live on the **PlayerState** by design, so they survive death, respawn, and possession changes. The pawn does not. Anything registered on that persistent state while capturing pawn-scoped context is holding a pointer to a corpse the moment the player dies. Two instances: the `StaleComponentRef` crosshair crash (`SteadfastComponentRef` going invalid after pawn destruction — fixed with `OnOwningPawnChanged`), and four attribute-change lambdas registered with `AddLambda` capturing the pawn's `this` (fixed with `AddWeakLambda`). The same logic is why `bAbilitiesGranted` never guarded the respawn grant path, and why `GA_Fire` reads `State.Reckoning` off the ASC rather than through the character. **Rule: if it lives on the PlayerState, ask the PlayerState — don't route through the pawn, and don't let a pawn-scoped bool answer a question about ASC state.**

**Standing gotcha #5 — a filed root cause is a hypothesis, and a wrong one costs more than none.** Added July 17, having just cost a session's opening. The boss disengagement defect sat in this document for two days with a confident, plausible, entirely wrong cause: perception drops the target. It was believed because the evidence fit — `left combat` mid-fight, no leash line, and a boss that froze. It was wrong because `OnPerceptionUpdated` has no clearing path at all, `left combat` is emitted by a damage-silence timer no AI code reads, and `SetMaxAge(5.f)` and `CombatExitGracePeriod = 5.f` are coincidentally the same five seconds. **The next session nearly opened by writing a perception guard for a bug that does not exist.** The actual cause — `CheckLeash` measuring from `PatrolOrigin` — was invisible because a *second* bug (missing Blackboard bools) prevented the chase that would have tripped it. **Rules: (1) a root cause written from a log without instrumenting the failure point is a guess, and should be recorded as one — "unknown, evidence suggests X" beats a confident wrong answer; (2) when two timers share a value, the log cannot distinguish them; (3) a bug that masks another bug is normal, not exotic — closing the first should re-open the question, not close it.** The diagnostic that settled it (`bDebugAIState` → `LogAIState`) samples every variable that could gate the BT from every source that writes one, on the leash timer that already runs at 2s. That pattern generalises.

**Standing gotcha, worth checking on every ability going forward:** discovered during tonight's cooldown debugging — the ability set was granting the raw C++ class (`GA_Read`) instead of the configured Blueprint child (`BP_GA_Read`), meaning every Blueprint-side value (cooldown effect, damage numbers, everything) was silently never reaching the running instance despite looking correctly configured in the editor. Worth explicitly re-confirming every ability in the ability set is granting its `BP_GA_X` variant, not the bare C++ class, since this exact mistake could easily have been made more than once and would produce no compile error and no obvious symptom beyond "my Blueprint changes don't seem to do anything."

**Standing gotcha #7 — Expose on Spawn variables are not populated when Event Construct fires.** Added July 21 after all seven equipment slot entries displayed “PrimaryWeapon” regardless of their actual enum value. `Create Widget` sets Expose on Spawn variables, but `Event Construct` fires before the assignment is committed. **The fix pattern:** move all display logic from Event Construct into an explicit function (e.g. `RefreshSlotDisplay`) and call it from the parent widget after `Create Widget` returns. Same issue affects `WBP_InventoryItemEntry` — any widget using Expose on Spawn for initial display needs this pattern.

**Standing gotcha #8 — `UWidget::Slot` shadows parameter names.** Added July 21. UHT rejects any `UFUNCTION` parameter named `Slot` in a `UUserWidget` subclass because `UWidget` already has a `Slot` property. Use `EquipSlot` or another name. The error is a compile-time `shadowing is not allowed` — caught early, but the rename must be applied in both header and cpp or the cpp function signature won’t match.

**Standing gotcha #9 — Double-binding delegates from PossessedBy + OnRep_PlayerState.** Added July 21. `InitGASFromPlayerState` is called from both paths. Any `AddDynamic` without a preceding `RemoveDynamic` triggers an ensure failure: `InvocationList[CurFunctionIndex] != InDelegate`. **The fix pattern:** `RemoveDynamic` immediately before `AddDynamic` on every delegate subscription in `InitGASFromPlayerState`. The `bAbilitiesGranted` flag already guards ability grants but not delegate subscriptions.

**Standing gotcha #10 — Material editor gotchas for overlay materials.** Added July 21. Three traps found while building M_VitalOverlay: (1) `Used with Skeletal Meshes` usage flag must be checked or the material is invisible on skeletal meshes; (2) `VectorParameter`’s RGB output pin produces the full XYZ vector — using the individual B output produces Z-only, creating a horizontal band instead of a spherical falloff; (3) `DoubleVectorParameter` is invisible to `SetVectorParameterValue` at runtime — use `VectorParameter` exclusively for parameters set from C++/Blueprint.

**Standing gotcha #11 — BT tasks lie about ability completion.** Added July 22, surfaced during engagement distance work. `BTTask_ActivateAbilityByTag` calls `TryActivateAbilitiesByTag`, GAS accepts activation, and the task returns `Success` on the same frame — but the ability is still mid-montage with its damage window not yet open. The BT has already moved on to the next Selector child. Currently masked by `FallingLateralFriction = 0` on Charge (nothing can overwrite her mid-leap) and by cooldown GEs preventing re-activation, but the lie surfaces the moment attack frequency is tuned or any ability needs to not be interrupted mid-execution. **The bridge exists but is incomplete:** `GothicBTService_CombatSync` syncs ability *readiness* (cooldowns, costs, blocked tags) into Blackboard bools, but does not sync *execution state* (is an ability currently active and when does it end). The correct fix is either a `State.Attacking` tag from `ActivationOwnedTags` synced through CombatSync into a `bIsAttacking` Blackboard bool that decorators gate on, or a custom BT task that returns `InProgress` and listens for `OnGameplayAbilityEnded`. The tag path uses existing infrastructure on both sides; the custom task is architecturally cleaner but adds a new async lifecycle to manage.

**Standing gotcha #12 — a new enemy takes no player ranged damage until its mesh blocks `ECC_Weapon`.** Added July 26 after it hid on the boss for the entire time she was being built. `GA_Fire` traces `ECC_Weapon`; the stock `CharacterMesh` collision profile has no response for it, so a mesh left on the default is transparent to every shot while melee, Slicer and any directly-applied GameplayEffect all work normally. The Thrall and the Feral Retained carry a Custom profile with `Weapon: ECR_Block`; copy that onto every new enemy. **Two compounding traps:** (1) a **placed** actor freezes its collision profile at placement time, so fixing the Blueprint alone does not fix the instance — the level actor must be re-placed or overridden directly (the same pattern as `LootTable` and `StartupAbilities`); (2) **the PIE harness's `apply_damage` never traces**, so any damage test driven through it will pass against an enemy a player cannot actually hit. If a boss's whole verification history runs through scripted damage, the delivery path has never been tested. Verify with a real shot and a health number.

**Standing gotcha #13 — a duplicated GameplayEffect keeps the original's tags.** Added July 26. `GE_ReadState` was duplicated from `GE_ReckoningState` and the granted tag was never swapped, so The Read granted `State.Reckoning` — four seconds of guaranteed vital hits — while its own consumer checked a tag nothing ever set. Neither half complains: the wrong tag is a *valid* tag, so the effect works perfectly and does someone else's job, and the intended feature simply never fires. Duplication is the fastest way to author a GE and will stay the workflow; the rule is to read the granted-tag list first, before anything else, on every duplicated effect.

### Explicitly Not Gating — valuable, correctly deferred, does not block the slice

- **Encounter reset (distinct from the spatial leash)** — identified July 15, correctly deferred. The existing `LeashRange` mechanic answers "the enemy wandered too far from home, reset it," which protects the open world from wandering trash and is *wrong for a den boss* — she can't leave the rotunda, so it guards against a case that can't happen. The real MMO problem is different: eight Antecedents pull her, seven die, one runs — she's still standing in her den at 30% health, so distance-based leashing never fires and the next Kindle inherits a half-won fight. A real encounter reset triggers on "no living Antecedent inside the volume for N seconds" (which `AGothicEncounterVolume` is now positioned to answer, having a TriggerBox as of July 15) and *restores* rather than clears: health to max, phase to 1, vital unfrozen, collapse timer killed, zones restored, walk back to origin. Note two things built during the slice are one-way and will need undoing: `FreezeVitalPoint` is explicitly documented as non-reversible, and `bAggroTriggered` latches permanently. Both are correct for a slice; both are what encounter reset has to reverse. Not slice scope.
- **Weapon slot expansion (Sidearm/Piece/Rig with distinct archetypes)** — Steadfast's design doesn't require three weapons to exist to be internally coherent, only for the tier *contrast* to be demonstrable. One weapon with correct tier logic (item 8 above) satisfies the slice; a second and third weapon are a stretch goal, not a requirement, unless the explicit goal of the demo becomes "show weapon variety" specifically.
